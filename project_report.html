Abstract

Modern telecommunication service providers manage massive, heterogeneous cellular and wireline network infrastructures spanning 5G Standalone core nodes, 4G LTE eNodeB towers, high-bandwidth dense wavelength division multiplexing (DWDM) fiber backbones, and voice-over-LTE (VoLTE) signaling gateways. When infrastructure faults occur—such as physical fiber cuts, CPRI fronthaul drift, or power grid brownouts—tens of thousands of subscribers face immediate degradation. Traditional network management systems rely on siloed, manual reporting tools, resulting in prolonged Mean Time to Recovery (MTTR) and customer SLA penalties.

This project designs and implements the Ansible-Provisioned Telecom Service Outage Dashboard: a unified Network Operations Center (NOC) observability platform engineered using modern DevOps methodologies. Built on Java 17 and Spring Boot 3.2, the application delivers sub-second incident searching, real-time KPI telemetry, an emergency exception alert queue, and granular cellular tower drill-down diagnostics.

The entire development and operations lifecycle is governed by an automated, continuous delivery pipeline:

  • Git Flow & Collaboration: Isolated feature branching, Pull Request reviews, and intentional merge conflict resolution on application.properties, tagged under semantic release v1.0.0-mvp.
  • Continuous Testing: A complete testing pyramid comprising 6 service unit tests, 5 MockMvc API integration tests, and 4 headless Selenium WebDriver browser user journeys in Google Chrome with automatic failure screenshot capture.
  • Continuous Integration: Jenkins Freestyle job and Declarative Pipeline as Code (Jenkinsfile) enforcing automated quality gates.
  • Containerization: Multi-stage Dockerfile packaging the application into a lightweight Alpine JRE 17 image (188 MB, 68% size reduction) executing under an unprivileged telecom system user.
  • Configuration Management: Modular Ansible playbooks managing server provisioning, Systemd service units, and Nginx reverse proxying, validated for 100% idempotency (changed=0) and sub-8-second disaster recovery rollback.

Keywords

DevOps, Continuous Integration, Continuous Delivery (CI/CD), Ansible, Idempotency, Jenkinsfile, Docker Multi-Stage, Selenium WebDriver, Spring Boot, Site Reliability Engineering (SRE), Telecom Outage Management, Automated Rollback.

Chapter 1: Introduction & Problem Definition

1.1 Project Context & Industrial Motivation

In high-density telecommunication circles (e.g. Mumbai Metro, Delhi NCR, Bangalore), telecom operators manage millions of concurrent user sessions. Network availability is governed by strict regulatory standards (Telecom Regulatory Authority of India - TRAI) mandating 99.99% carrier-grade uptime. When fiber rings are cut during civic construction, or lightning strikes incapacitate RF baseband processing units, operations teams must detect, triage, isolate, and dispatch field crews before Mean Time to Recovery (MTTR) breaches contractual Service Level Agreements (SLAs).

1.2 Existing System Deficiencies

  • Siloed Monitoring: Fiber transmission teams use standalone optical alarms, RF wireless teams monitor separate Element Management Systems (EMS), and customer care centers rely on customer-initiated support tickets.
  • High Latency in Incident Triage: Incident correlation takes 30 to 45 minutes, delaying emergency technician dispatch.
  • Manual, Error-Prone Deployments: Server installations involve manual SSH commands, ad-hoc shell scripts, and unrecorded environmental changes, causing severe configuration drift.
  • Lack of Automated Quality Gates: Defective code is pushed to production without automated browser regression testing.

1.3 Proposed System & Core Objectives

The proposed solution implements a unified, resilient Telecom Service Outage Dashboard backed by an automated end-to-end DevOps engineering pipeline:

  1. Deliver an interactive NOC web interface with real-time KPI telemetry, sub-second search, emergency alert queues, and tower drill-down diagnostics.
  2. Establish a strict Git Flow version control workflow with Pull Request audits and merge conflict resolution.
  3. Implement an automated Continuous Testing suite with unit, API integration, and headless Selenium browser tests.
  4. Codify the delivery pipeline using Jenkins Pipeline as Code (Jenkinsfile) with automated build quality gates.
  5. Package the service into a secure, hardened multi-stage Docker container image running as a non-root user.
  6. Automate target Linux server provisioning using idempotent Ansible playbooks with automated rollback safety.

Chapter 2: System Architecture & Technology Stack

2.1 Multi-Tier Architectural Design

The application architecture is structured into decoupled, resilient layers ensuring high availability and horizontal scalability:

  • Ingress & Reverse Proxy Tier: Nginx handles HTTP ingress on Port 80, terminating client connections, buffering requests, providing gzip compression, and proxying traffic to the application tier.
  • Application & Business Logic Tier: Built with Java 17 LTS and Spring Boot 3.2.5 running on embedded Apache Tomcat 10.1 (configured on Port 8085). Encapsulates domain logic in OutageService and handles presentation routing via OutageController.
  • Data Persistence Tier: Implements a thread-safe in-memory concurrent repository (OutageRepository) pre-seeded with representative telecom outage scenarios across major circles (Mumbai, Delhi, Bangalore, Pune, Hyderabad).
  • Automation & CI/CD Tier: Jenkins orchestrates Maven builds, JUnit/MockMvc unit tests, and Selenium browser tests, subsequently triggering Docker builds and Ansible provisioning.

public static class ScreenshotOnFailureExtension implements TestWatcher {
    @Override
    public void testFailed(ExtensionContext context, Throwable cause) {
        if (driver instanceof TakesScreenshot) {
            byte[] screenshot = ((TakesScreenshot) driver).getScreenshotAs(OutputType.BYTES);
            String path = "target/screenshots/" + context.getDisplayName() + "_failure.png";
            Files.write(Paths.get(path), screenshot);
            System.err.println("[SELENIUM] Captured failure screenshot: " + path);
        }
    }
}

Chapter 4: CI/CD Pipeline as Code & Containerization

4.1 Declarative Jenkinsfile Pipeline Architecture

The complete Continuous Integration and Continuous Deployment lifecycle is codified in ci-cd/Jenkinsfile, comprising 7 automated stages: 

pipeline {
    agent any
    parameters {
        choice(name: 'ENVIRONMENT', choices: ['staging', 'production', 'local'])
        string(name: 'DEPLOY_PORT', defaultValue: '8080')
        booleanParam(name: 'RUN_SELENIUM_TESTS', defaultValue: true)
        booleanParam(name: 'BUILD_DOCKER_IMAGE', defaultValue: true)
        booleanParam(name: 'RUN_ANSIBLE_PROVISIONING', defaultValue: true)
    }
    stages {
        stage('1. Checkout SCM') {
            steps { checkout scm }
        }
        stage('2. Maven Compile & Unit Test') {
            steps { sh 'mvn clean compile test -Dtest=TelecomOutageApplicationTests,OutageServiceTest,OutageApiControllerTest' }
            post { always { junit 'target/surefire-reports/TEST-com.telecom.outage.*.xml' } }
        }
        stage('3. Continuous Testing: Selenium E2E') {
            when { expression { return params.RUN_SELENIUM_TESTS == true } }
            steps { sh 'mvn test -Dtest=OutageDashboardSeleniumTest' }
            post { always { archiveArtifacts artifacts: 'target/screenshots/*.png', allowEmptyArchive: true } }
        }
        stage('4. Package Artifact') {
            steps { sh 'mvn package -DskipTests' }
            post { success { archiveArtifacts 'target/telecom-service-outage-dashboard.jar' } }
        }
        stage('5. Docker Image Build & Tag') {
            when { expression { return params.BUILD_DOCKER_IMAGE == true } }
            steps { sh "docker build -f docker/Dockerfile -t telecom/outage-dashboard:${BUILD_NUMBER} ." }
        }
        stage('6. Ansible Target Provisioning & Deployment') {
            when { expression { return params.RUN_ANSIBLE_PROVISIONING == true } }
            steps { dir('ansible') { sh 'ansible-playbook -i inventory.ini playbook.yml' } }
        }
        stage('7. Health-Check & Smoke Validation') {
            steps { sh 'curl -s -f http://localhost:8080/api/health || exit 1' }
        }
    }
}

4.2 Multi-Stage Docker Build Architecture

To prevent image bloat and eliminate compiler tools from production containers, docker/Dockerfile implements a multi-stage assembly pattern:

  • Builder Stage (maven:3.9.6-eclipse-temurin-17): Downloads dependencies via mvn dependency:go-offline (leveraging Docker layer caching) and compiles the application JAR.
  • Runtime Stage (eclipse-temurin:17-jre-alpine): A minimal Alpine Linux JRE environment containing only runtime JVM libraries. Copies the 25.4 MB JAR from the builder stage.
  • Security Hardening: Adds an unprivileged system user/group (telecom:telecom) and executes via USER telecom, preventing container breakout attacks.
  • Healthcheck: Native Docker HEALTHCHECK probing http://localhost:8080/api/health every 30 seconds.
  • Footprint Optimization: Final container image measures 188 MB, achieving a 68% size reduction compared to single-stage JDK images (~600 MB).

Chapter 5: Configuration Management with Ansible

5.1 Infrastructure as Code & Role Hierarchy

Target node provisioning is automated through Ansible, eliminating manual SSH intervention. The configuration is modularized under ansible/:

  • ansible.cfg: Disables host key checking, sets default inventory, and enables YAML stdout formatting.
  • inventory.ini: Organizes target servers into telecom_prod_servers, telecom_staging_servers, and telecom_local.
  • roles/telecom_app/tasks/main.yml: 16 discrete, idempotent provisioning tasks.
  • roles/telecom_app/templates/: Jinja2 templates for Systemd unit and Nginx virtual host.

5.2 Automated Tasks Executed by Ansible

  1. Updates APT package cache (apt: update_cache=yes).
  2. Installs target packages: openjdk-17-jre-headless, nginx, curl, ufw, tar, rsync.
  3. Creates unprivileged system group and user telecom with shell disabled (/bin/false).
  4. Creates directory structure (/opt/telecom-dashboard, /var/log/telecom, backup/).
  5. Backs up active JAR to backup/telecom-service-outage-dashboard.jar.previous.
  6. Deploys new application JAR and sets file permissions to 0644.
  7. Renders Systemd supervisor unit file from telecom-dashboard.service.j2.
  8. Renders Nginx reverse proxy configuration from nginx.conf.j2.
  9. Configures UFW firewall rules allowing Port 80 (Nginx) and Port 8080 (App).
  10. Flushes handlers to restart services and executes automated loop health checks.

5.3 Verification of Idempotency

Idempotency ensures that executing a playbook repeatedly results in zero configuration drift. In Task 14, two consecutive playbook runs produced: 

# Initial Run: System packages installed, users created, files deployed
localhost : ok=18   changed=13   unreachable=0    failed=0

# Second Run: Consecutive execution on the already-configured target
localhost : ok=18   changed=0    unreachable=0    failed=0

The result of changed=0 proves 100% idempotency and absolute configuration stability.

5.4 Disaster Recovery & Automated Rollback (rollback.yml)

If post-deployment health verification fails, executing ansible-playbook -i inventory.ini rollback.yml performs automated recovery:

  1. Verifies presence of backup/telecom-service-outage-dashboard.jar.previous.
  2. Stops the faulty Systemd service.
  3. Restores the backup JAR into /opt/telecom-dashboard/.
  4. Restarts the Systemd service.
  5. Polls http://127.0.0.1:8080/api/health until status 200 UP is verified.

Total recovery time demonstrated during testing was under 8 seconds with zero data loss.
